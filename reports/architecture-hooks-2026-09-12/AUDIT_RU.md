# Foldwink: архитектура, игровой баланс, возвращаемость и визуальный перезапуск

Дата: 12 сентября 2026. Основа: локальный HEAD `e53ec33` плюс существующие незакоммиченные изменения. Это анализ текущей расширенной версии, не разрешение на удаление функций и не подтверждение готовности релиза.

## Вывод

Foldwink обладает подходящим ядром для короткого ежедневного ритуала: узнавание связей, ограниченный риск ошибки, раскрытие подсказок, приятная сборка найденной группы. Самое перспективное отличие — Foldwink Tabs + осмысленный выбор момента Wink. Архив, коллекция и дружеский вызов могут усиливать эту основу.

Сейчас накопление функций опередило настройку игрового ритма. Главные проблемы: скачущая последовательность сложности; задержка знакомства с фирменной механикой; награды, не связанные с уникальным завершением; обещания контракта, не реализованные движком; обязательное прерывание результата конвертом; перегруженное меню. Ещё одна библиотека эффектов сама этого не исправит.

Предыдущая рекомендация из handoff автоматически вернуться к старому минималистичному составу была слишком категоричной. Текущие ограничения и реализованные возможности расходятся, но решение о составе продукта следует принимать по ценности механик и результатам плейтеста. Для данного аудита ничего из игры не удалялось.

## 2. Архитектура: что сохранить и что исправить

### Удачная основа

React + TypeScript + Zustand подходят этой игре. Для 16 DOM-кнопок не требуется игровой движок. Чистые функции проверки групп, отдельные persistence observers, локальные JSON, языковые чанки, HTML-текст и CSS-трансформации — разумные решения. Переписывать приложение на Unity, Phaser или canvas ради внешнего вида нецелесообразно.

QR-генератор (`src/progression/qr.ts:166`) имеет ограниченную вместимость без ясной ошибки для чрезмерного payload. Оба участка разумно заменить стандартными решениями, сохранив свои продуктовые правила.

### Целевая структура без большого переписывания

```text
Экран → команда попытки → чистый игровой движок
                              ↓
                    единая финализация результата
                              ↓
                 статистика + прогресс + receipt награды
                              ↓
                сохранение → отображение → feedback
```

Нужен `attemptId`, неизменяемые `puzzleId/contentVersion/rules`, `countsToStats`, `rewardEligibility`, завершённый результат. Повторная доставка события должна давать тот же результат без повторного начисления. Не следует путать idempotency одной попытки и правило «не фармить один puzzle в новых попытках»: нужны оба ограничения. Daily удобно учитывать по date/language, обычную коллекцию — по принятому правилу уникального завершения.

Сначала достаточно одной согласованной записи локального прогресса и квитанций с версией схемы. IndexedDB и дополнительные библиотеки нужны только при доказанной необходимости транзакций между большими наборами данных.

### Производительность

Новая диагностическая сборка: app JS **715.44 kB / 152.84 kB gzip**, EN **879.67 / 188.29**, RU **923.62 / 209.47**, DE **981.41 / 182.33**, CSS **63.84 / 15.17**. Это размеры файлов, не замер фактически переданных байтов или времени загрузки.

Английский пул импортируется eagerly, даже когда далее загружается RU/DE. Следует вынести редко используемые Passport/Palimpsest/QR/share-renderer в lazy chunks и поставлять игровую часть JSON без редакторских rationale. Следующая ступень — небольшие заранее собранные контент-пакеты с манифестом и offline-кешированием. Не нужно превращать один чанк в тысячу отдельных сетевых запросов.

У `Card.tsx:134` rAF останавливается лишь после возврата tilt к нулю; ненулевое стабильное положение может продолжать цикл. Reduced-motion CSS не покрывает `.fw-deal`, добавленный позднее (`index.css:612,646`), и JS-gyro остаётся активен. Решение — прекращать расчёты при достижении текущей цели, отключать движение при reduced-motion и неподходящем pointer/device. Это анализ кода, не замер расхода батареи.

## 3. Игровой баланс: главный рабочий приоритет

### Текущее распределение не является калибровкой

| Язык | Easy | Medium | Hard |
|---|---:|---:|---:|
| EN | 523 | 443 | 34 |
| RU | 621 | 379 | 0 |
| DE | 577 | 423 | 0 |

В EN текущий metadata score (`editorialRank`, иначе `difficultyScore`) имеет диапазоны Easy **4–76**, Medium **8–81**, Hard **15–70**. Эти значения редакторские/эвристические, не человеческие рейтинги сложности; разные источники могли оценивать неодинаково. Перекрытие диапазонов само по себе не доказывает плохие пазлы, но такую шкалу нельзя считать надёжной моделью подбора.

Hard в RU/DE сейчас может подменяться английским контентом (`src/puzzles/byLang.ts`). Для игрока это скачок языковой компетенции, а не честное увеличение логической сложности. В продукте это надо прямо обозначить или не предлагать как обычный следующий уровень.

### Как устроить хороший темп

Особенно важен первый запуск: `src/app/App.tsx:41` после завершения или пропуска onboarding запускает `startDaily()`, который выбирает из всего допустимого пула. Два стандартных starter-пазла поэтому не гарантируют лёгкий первый опыт. Учебный старт нужно назначать явно и не выдавать его за общий пазл дня.

После проигрыша Standard cursor не продвигается (`store.ts:576`), поэтому детерминированный picker снова выбирает ту же доску. Нужны честно различённые действия «Повторить» и «Другой пазл», а калибровка сложности должна отдельно учитывать первую и повторные попытки.

1. **Первые 5–8 досок — отдельная отредактированная последовательность.** Простая понятная группа для первого успеха, затем две более интересные связи. Новизна вводится по одному элементу. Обучение не должно начинаться с валют, контрактов и коллекций.
2. **Дать познакомиться с Wink рано.** Сейчас Medium закрыт до пяти Easy-побед (`readiness.ts:38`), а Easy не имеет фирменного twist. Предлагаю управляемую пробную доску с Tabs/Wink после первой обычной победы; дальнейшую сложность рекомендовать по результатам, а не требовать долго доказывать право попробовать отличительную механику.
3. **Управлять сложностью подбора, а не ответами.** В практике выбирать из небольшого диапазона проверенной сложности, учитывать последние завершения, повторяемость темы, историю ошибок. После затруднения предлагать более доступную доску явно. Не менять правильные группы или лимит ошибок посреди игры.
4. **Daily фиксирован для языка/даты.** Для него не использовать скрытую персональную коррекцию ответов или сложности. Учебная последовательность новичка отделена от общего daily.
5. **Четыре ошибки оставить исходной базой.** Сначала исправить качество и последовательность контента. Механическое увеличение числа попыток может скрывать неоднозначность, но не делает её интересной.
6. **Не отнимать попытку за ту же ошибочную четвёрку.** Хранить нормализованные наборы прошлых ответов; повтор показывать как «это сочетание уже проверяли». Это новая предлагаемая UX-политика, ещё не реализованная.
7. **После ошибки должно быть понятно, чему научился.** После завершения давать краткое объяснение спорной связи. Если разумное альтернативное разбиение существует, доску переписывать; объяснение автора не делает произвольный ответ справедливым.
8. **Учитывать структуру 4×4.** После трёх групп последняя четвёрка уже предопределена. Самый содержательный момент открытия часто наступает раньше последнего submit. Финальная анимация должна завершать достигнутое понимание, не затягивать механический остаток.

Для каждой отобранной доски полезно хранить: знакомость слов, тип связи, опорную группу, риск альтернативной группировки, качество hint, плановый tier, результаты человеческого плейтеста. Длинные слова, малоизвестные факты и языковые кальки не заменяют интересной логики. Выборка/валидация в этом аудите не является редакторским одобрением всех активных досок.

### Как проверять «реально затягивает»

Нельзя доказать возвращаемость количеством эффектов или тестов. Следующая проверка — 20–30 представителей целевой аудитории, с раздельным учётом языка и опыта. Для качественного первого исследования этого достаточно, для уверенных A/B-выводов — нет. Люди играют без подсказок разработчика; повторный визит оценивается отдельно от завершения назначенного теста.

Стартовые проектные гипотезы, **не отраслевые нормы и не обещания**:

| Режим | Доля побед подходящих ему игроков | Время успешного решения |
|---|---|---|
| Учебные первые доски | 85–95% | 1–3 минуты |
| Основная повседневная игра | 65–80% | 2–5 минут |
| Добровольный сложный вызов | 35–55% | 4–8 минут |

Дополнительная стартовая цель — первая самостоятельно найденная группа за 20–45 секунд. Собирать медиану и длинный хвост времени, долю выходов без submit, точку первого затыка, Wink до/после затруднения, переход к следующей доске, причины «слишком легко/нечестно», D1/D7. Не оптимизировать лишь общее время в игре: оно растёт и от мучительного интерфейса.

После первых наблюдений выбрать компактный проверенный набор, а не пытаться сразу откалибровать 3 000 досок. Рекомендуемый пилот — 30 досок: 10 для входа, 15 основных, 5 сложных, отдельно для выбранного первого языка. Дальнейшее расширение — по той же редакторской процедуре.

## 4. Hooks: что усиливать

| Слой | Что должно притягивать | Конкретное решение |
|---|---|---|
| 5–30 секунд | Узнать связь | Читаемые карточки, быстрый выбор, первая понятная группа |
| 2–5 минут | Довести гипотезу до решения | Честная ошибка, осмысленный Wink, приятное превращение четвёрки в найденную категорию |
| Следующий пазл | «Теперь попробую чуть сложнее» | Видимая кнопка продолжения, подходящая следующая доска, минимум обязательных экранов |
| Следующий день | Новая хорошая задача | Постоянный daily-календарь и небольшой личный след в коллекции |
| Социальный повод | «Интересно, как ты это решишь» | Один понятный share/challenge flow с тем же puzzle identity |

Коллекция имеет смысл как память о мастерстве: первая чистая победа, освоение Wink, несколько разных типов связи. XP/Ink/Prestige без понятного использования создают визуальный шум. У Ink сейчас не видно полноценного расходования; разумно оставить один ресурс для оформления либо вообще показывать постоянные достижения вместо валюты.

Случайный 45%-ный drop штампа и обязательный конверт после каждой победы — слабая замена интересной следующей доске. Конверт может стать красивым редким событием при достижении milestone; обычную награду лучше показать inline и сразу дать продолжить. Коллекционные награды — постоянные; пропуск дня не должен отнимать их.

Zen стоит либо честно назвать серией испытаний, либо действительно убрать из него давление текущей win streak. Контракт можно сохранить как факультативную проверку мастерства с точными условиями и косметическим результатом. Palimpsest интересен как отдельный эксперимент после освоения базы, но не как ещё одна равноправная кнопка первого запуска. Это предложения для выбора направления, не автоматически принятые новые правила.

## 5. Радикальный визуальный перезапуск

### Что видно сейчас

На 1440×900 основные menu-кнопки ограничены шириной 240 px, выстроены в длинную колонку; меню имеет высоту 989 px. На 390×844 меню высотой 947 px уводит настройки вниз. Поле, наоборот, занимает около верхней трети телефона, а ниже остаётся большая пустая область. Правило `@media (max-width:400px), (max-height:600px)` было описано как extension-compact, но действует и на высокий телефон 390×844: карточки принудительно 52 px.

У светлых карточек на тёмном фоне заметный светящийся контур; масса теней, рамок и эмодзи создаёт смешанную материальность. На экране результата четыре share-действия идут раньше следующего пазла. Конверт закрывает только что достигнутый результат. Это наблюдения по реальному интерфейсу, а не макету.

### Рекомендованное направление: Paper Theatre

Уютная авторская настольная головоломка: светлая бумага, глубокий чернильный цвет, один акцент сургуча, тактильная печать. Название направления условное.

- **Главный экран:** большая карточка «Сегодня», дата и один главный CTA; маленькое превью поля без спойлера категорий. Практика и Коллекция — два вторичных входа. Настройки — компактный отдельный слой. Сложные режимы открываются внутри практики/коллекции, не конкурируют с daily.
- **Поле:** занимает полезную площадь телефона. Стартовый ориентир высоты карточки 64–76 px, затем проверка с настоящими длинными RU/DE словами. Текст 14–16 px там, где это позволяет отредактированное содержимое; нельзя достигать fit только уменьшением шрифта. Неподвижный, предсказуемый ряд управляющих кнопок.
- **Материал:** матовая карточка с тонким торцом и одной контактной тенью; свет приходит с одной стороны. Текстура низкого контраста не проходит через область чтения. Убрать белое свечение как основной способ показать объём.
- **Типографика:** выразительный заголовочный шрифт и спокойный читаемый шрифт карточек, с полноценными латиницей/кириллицей. Фиксированные роли для заголовка, задачи, метаданных. Не превращать каждую подпись в uppercase microtext.
- **Графика:** небольшой согласованный SVG-набор вместо разнородных emoji; собственные печати и уголок сгиба. Один характерный знак Foldwink важнее десятка декоративных иконок.
- **Главный визуальный момент:** четыре выбранные карточки аккуратно собираются и складываются в полосу найденной категории. Wink раскрывает бумажный край. Удачный пазл оставляет печать на итоговой карточке. В спокойном состоянии поле неподвижно.
- **Результат:** компактный итог, одно объяснение/достижение, «Ещё пазл» или daily-завершение, единая кнопка «Поделиться». Награда не блокирует результат; отдельная большая церемония только при редком milestone.
- **Темы:** не четыре одинаковых тёмных палитры. Сначала закончить один светлый и один тёмный вариант с теми же правилами материалов и размеров.

Альтернативное направление — яркая редакционная игра с плоскими крупными цветовыми блоками, строгой типографикой и короткими упругими переходами. Она лучше передаёт энергичность, но слабее использует уже имеющийся образ бумаги, архива и печатей. Для Foldwink я выбрал бы Paper Theatre.

Ориентиры motion для прототипа: нажатие 80–120 ms, сборка группы 350–500 ms, редкая печать до 700 ms с возможностью быстро продолжить. Это художественные стартовые параметры, не доказанные оптимумы. Смысл анимации должен читаться также при выключенном звуке и reduced motion.

PixiJS/Three.js/Phaser не являются разумным первым шагом: DOM хорошо подходит читаемым 16 карточкам и доступности; полноценная render-система добавит отдельную инфраструктуру. Pixi действительно предоставляет canvas application, но это другая архитектурная обязанность, не автоматический апгрейд качества дизайна. [Pixi application](https://pixijs.com/8.x/tutorials/getting-started).

Действующий AGENTS.md запрещает motion-библиотеки и дополнительные механики. Пользователь попросил оценить их возможность, поэтому здесь сравнение допускается; установки и пересмотра правил не происходило. Для будущего внедрения достаточно явно принять выбранное направление, не нужно подключать весь список. Размер runtime, конкретную версию и её лицензию фиксировать по выбранному пакету при реализации, без неподтверждённых обещаний «это почти ничего не весит».

## 7. Порядок следующей работы

1. Исправить базовую честность: попытка/receipt награды, условия контракта, replay, fixed daily. Проверять повторную финализацию, потерю/возврат вкладки, окончание суток и импорт состояния.
2. Настроить 30-досочный пилот и первую последовательность. Тестировать опорные группы, неоднозначность, смысл Wink, отказ от повторной ошибки и осмысленный следующий пазл.
3. Сделать один полнофункциональный визуальный срез Paper Theatre: Menu → Game → Result, mobile-first, затем 1024×768 и 1440×900. Включить длинную RU/DE карточку, ошибку, win/loss, клавиатуру, reduced motion.
4. Провести человеческий плейтест и недельное наблюдение добровольного возвращения; исправить конкретные точки скуки/нечестности. Не объявлять баланс удачным только по проценту побед.
5. После этого расширять контент и коллекцию. Измерять новые события только через существующую понятную privacy/consent-поверхность. Сейчас allowlist пропускает daily/standard, но теряет zen (`src/analytics/eventLog.ts:151`); новые hooks почти не имеют отдельных событий. Простых суммарных счётчиков недостаточно для корректных когорт D1/D7.

Предпочтительный следующий результат — короткий, действительно играбельный и измеримый вертикальный срез. Он покажет и качество баланса, и новый визуальный язык; массовая полировка всех дополнительных режимов до этого даст меньше полезной информации.
