## 0. Как читать и исполнять ТЗ

Этот документ превращает рекомендации аудита в проверяемые требования. Он не означает, что пользователь уже видел, принял или протестировал будущий дизайн. Выбранные здесь продуктовые решения — предлагаемые рабочие defaults для реализации. Изменять их следует через короткую запись решения с причиной, влиянием на данные и критериями проверки.

- **MUST** — обязательное условие соответствующего этапа.
- **SHOULD** — реализовать, если не обнаружено документированного препятствия; отсрочку записать.
- **OPTIONAL** — отдельный эксперимент, не зависимость основного выпуска.
- **P0** — целостность результата, сохранений и обещаний игроку.
- **P1** — баланс, первое впечатление, основная игровая петля.
- **P2** — выразительность, удобство возвращения, эксплуатационная надёжность.
- **P3** — необязательные расширения и экспериментальные инструменты.

Идентификаторы `ARCH-*`, `GAME-*`, `CONTENT-*`, `UX-*`, `OPS-*`, `TEST-*` используются в задачах, тестах и отчётах. «Реализовано» и «проверено на staging» — разные состояния. Непроверенный критерий не считается пройденным.

### 0.1. Главный результат

Игрок понимает задачу, быстро находит первую осмысленную связь, получает понятную обратную связь, замечает фирменный Wink, завершает короткую партию и добровольно выбирает следующую. Возвращение строится на интересе к задачам, освоении приёма и красивой личной коллекции, а не на страхе потерять накопленное.

Нельзя обещать «игра точно затянет» по исходному коду или автоматическим тестам. ТЗ задаёт гипотезы, механизмы и человеческие проверки, которыми это подтверждается либо опровергается.

### 0.2. Что не входит в текущую работу

Не выполнять автоматически: переписывание приложения на игровой движок, создание backend, аккаунтов, рейтингов, сетевой синхронизации, новых платных преимуществ, покупку инструментов, массовую генерацию контента, установку новых SDK, изменение production или публикацию в магазинах.

Нативная iOS-оболочка, расширение и side panel не должны ломаться от общего кода, но их полноценная публикация — отдельные платформенные ворота. Основной целевой продукт этого ТЗ — адаптивный web/PWA.

## 1. Проверенная исходная точка

- React 18 + TypeScript + Vite, Zustand для UI-состояния, чистый игровой движок.

## 3. Инварианты игры и определения

### 3.1. Термины

- **Puzzle lineage** — долговечная идентичность одной редакционной задачи. Исправление опечатки сохраняет lineage; совершенно новая задача получает новый.
- **Content version** — неизменяемая редакция текста и групп конкретной задачи.
- **Attempt** — одна начатая попытка, получающая уникальный `attemptId` до первого хода.
- **First encounter** — первый старт данной language/lineage в профиле вообще, а не первая победа. Отдельное `firstInContext` отмечает первый старт в данном статистическом контексте; эти признаки нельзя смешивать.
- **Replay / retry** — новая попытка уже показанной задачи; не новая уникальная задача.
- **Daily identity** — локальная календарная дата старта + язык + опубликованная запись календаря.
- **Reward receipt** — сохранённый результат единственного решения о награде; UI его отображает, но не создаёт заново.
- **Completion** — терминальное win/loss. Прерванная партия — отдельный статус abandoned, не подставная победа/поражение.
- **Qualified session** для исследования — реальный участник начал хотя бы одну доску; автоматизация, разработчики и назначенные исследовательские визиты маркируются отдельно.

### 3.2. Непереговорные инварианты

**GAME-01.** На входе движка ровно 16 уникальных item IDs, 4 непересекающиеся группы по 4. Отображаемый текст не является идентификатором.

**GAME-02.** Submit принимает ровно четыре различных ещё не решённых item IDs. Невалидный ввод, двойное событие клика и повтор прежней неверной четвёрки не увеличивают ошибки.

**GAME-03.** Обычная партия проигрывается на четвёртой уникальной неверной попытке. Все группы решены → победа. Из terminal-состояния нельзя сделать игровой ход.

**GAME-04.** Начатая партия фиксирует контент, правила, режим, язык и daily date. Обновление приложения, смена языка меню, открытие tier или полночь не меняют текущие ответы.

**GAME-05.** Один `attemptId` финализируется один раз. Награда одного уникального основания выдаётся максимум один раз, даже если созданы разные attempt IDs.

**GAME-06.** Использование Wink не делает победу «неполноценной», не уменьшает базовый XP и не требует оплаты/рекламы. Факт решения без Wink может отображаться нейтральной дополнительной отметкой.

**GAME-07.** Звук, вибрация, анимация, аналитика и сеть не влияют на правильность, доступность управления и начисление результата.

**GAME-08.** Daily одного языка и даты одинаков для новичка и ветерана. Персональная рекомендация существует только в практике.

## 4. Архитектура исполнения

### 4.1. Целевая схема

```text
Bootstrap → storage ready → migrations → selected-language manifest → Zustand UI
UI command → application service → pure engine / eligibility policy
                                 → atomic persistence transaction
                                 → committed state + receipt → UI
                                                        └→ feedback / optional telemetry
```

Ни один React render, `useState` initializer, modal mount или effect повторного показа не имеет права начислять XP, менять win/loss, тратить валюту или создавать completion. Повторный рендер должен быть безопасным.

### 4.2. Модули и ответственность

Имена новых файлов — целевая структура, а не утверждение об их существовании.

| Модуль | Ответственность | Запрещено |
|---|---|---|
| `src/game/engine/` | Проверка выбора, ход, исход по фиксированным rules | React, storage, Audio, analytics, Date.now внутри расчёта |
| `src/game/application/attemptService.ts` | Start, submit, wink, abandon, finalize; проверка revision | Начисление из UI; доверие произвольному state из ссылки |
| `src/game/application/rewardPolicy.ts` | Чистое вычисление eligibility и детерминированного receipt | Случайный дроп, запись напрямую в браузер |
| `src/game/application/statsPolicy.ts` | Раздельные first-attempt, replay, daily и practice результаты | Вывод «сложность пройдена» из количества фарм-побед |
| `src/game/state/` | Представление зафиксированного состояния и transient selection/UI | Самостоятельные конкурирующие persistence observers |
| `src/persistence/` | Транзакции, bootstrap, migration, export/import, quota handling | Незаметная замена повреждённого профиля пустым |
| `src/puzzles/catalog/` | Manifest, версии, chunk loading, calendar lookup | Выдача EN при неизвестном RU/DE ID |
| `src/puzzles/progression.ts` | Чистый подбор из проверенных bands | Независимые записи seed/cursor при каждом рендере |
| `src/audio/` + `src/feedback/` | Один управляемый аудиоконтур, haptics и reduced motion | Побочные изменения игрового результата |
| `src/screens/` | Menu, Game, Result, Stats/Collection | Экономика и восстановление хранилища внутри компонентов |

Не вводить универсальный event-sourcing framework, DI-container, CQRS или отдельный state-machine runtime. Команды и переходы небольшого приложения реализовать обычными типизированными функциями.

### 4.3. Контракт попытки

**ARCH-01 / P0.** Расширить `src/game/types/game.ts`. Ниже — обязательный контракт полей; синтаксические детали допускают адаптацию к существующим типам.

```ts
type AttemptContext =
  | 'daily' | 'practice' | 'onboarding' | 'zen'
  | 'mastery' | 'archive' | 'duel' | 'custom' | 'palimpsest';

type PuzzleRef = {
  language: 'en' | 'ru' | 'de';
  puzzleId: string;
  lineageId: string;
  contentVersion: string;
};

type AttemptRules = {
  version: 1;
  maxIncorrectGuesses: number; // terminal threshold: normal loss on 4th; mastery on 2nd
  tabsEnabled: boolean;
  maxWinks: 0 | 1;
  timerPresentation: 'hidden' | 'optional';
};

type AttemptIdentity = {
  attemptId: string;
  puzzle: PuzzleRef;
  context: AttemptContext;
  rules: AttemptRules;
  startedAtUtcMs: number;
  startedLocalDate: string;
  startedTimeZone: string;
  daily?: { date: string; scheduleVersion: string; entryId: string };
  parentAttemptId?: string; // explicit retry
  challengeId?: string;
  firstEncounter: boolean;
  firstInContext: boolean;
};
```

Кроме identity хранить phase, revision, order, selection, solvedGroupIds, неправильные сигнатуры, mistakesUsed, winkedGroupId, накопленное активное время, endedAt, outcome и receiptId. Контент активной доски хранить как валидированный snapshot или гарантированно доступную pinned-версию: старый chunk нельзя удалять, пока попытка от него зависит.

`countsToStats` больше не универсальный переключатель всех политик. Его мигрировать в явные eligibility flags/функции. Разрешение статистики, коллекции и XP определяется отдельно.

`firstEncounter` ставится атомарно по первому start для `language + lineageId` во всех распознанных официальных контекстах и никогда не переносится на retry. Если этот первый start abandoned, history фиксирует first-encounter abandonment; последующая победа — replay, а не первая попытка для калибровки. `firstInContext` хранится отдельно по context identity: у daily это конкретный дневной слот, у practice — language/lineage/context. Калибровка practice требует одновременно `context === practice` и `firstEncounter === true`; уже увиденная в daily/duel/Zen задача не становится «незнакомой» при открытии practice. Неопознаваемую custom board нельзя надёжно сопоставить с официальной lineage; такой импорт вообще не участвует в калибровке.

### 4.4. Команды и финализация

**ARCH-02 / P0.** Каждая изменяющая существующую попытку команда содержит `commandId`, `attemptId`, `expectedRevision`; start/replace/import также несут `expectedProfileRevision` и ожидаемый `activeAttemptId` либо null. Движок получает injected timestamp/RNG только там, где они нужны; reward policy случайности не использует.

Алгоритм `submitSelection`:

1. Загрузить текущую attempt revision в транзакции; отклонить устаревшую команду с безопасной синхронизацией UI.
2. Проверить фазу, число и валидность item IDs.
3. Построить сигнатуру из отсортированных ID с однозначным кодированием, например JSON массива, а не неоднозначным соединением без delimiter escaping.
4. Если сигнатура уже была неправильной — вернуть non-consuming feedback; selection оставить для осмысленного изменения.
5. Иначе вычислить ход: группа решена либо добавить сигнатуру и одну ошибку.
6. При terminal outcome вычислить stats delta, unique reward key, receipt и collection changes.
7. Одной транзакцией записать attempt, terminal result, изменения профиля/статистики и receipt. Пометить command обработанной в рамках ограниченного журнала текущей попытки.
8. Только после commit опубликовать итог в UI. Audio/analytics получают committed event; их ошибка не откатывает игру.

Закрытие вкладки между пунктами 6–7 не оставляет «результат сохранён, награда нет» или наоборот. После сбоя приложение восстанавливает последний зафиксированный ход. Анимация может проигрываться повторно при явном просмотре, но не экономика.

### 4.5. Машина состояний

| Из | Событие | В | Обязательное поведение |
|---|---|---|---|
| loading | storage/catalog ready | ready | Не запускать пустые autosave observers раньше hydration |
| ready | start | playing | Зафиксировать attempt identity до первого выбора |
| playing | valid nonterminal submit | playing | Revision +1, feedback после commit |
| playing | terminal submit | completed | Результат и receipt атомарны |
| playing | quit → resume later | suspended | Сохранить; не создавать loss |
| playing/suspended | explicit abandon + new | abandoned | Подтверждение только если реально теряется текущая партия; next создаёт другой ID |
| completed | open result | completed | Read-only показ сохранённого результата |
| completed | retry | playing новой попытки | Parent ID, replay policy, без повторного daily record |
| any | storage write failure | recovery UI | Не заявлять «сохранено»; разрешить retry или явно временную сессию |

Не хранить `resolving` как невосстановимую фазу ожидания animationend. Игровое состояние может быть committed, пока слой представления доигрывает безопасную анимацию.

### 4.6. Хранилище и две вкладки

**ARCH-03 / P0.** Целевой вариант для атомарного ядра — browser IndexedDB с небольшой repository-обёрткой; не библиотека синхронизации и не backend. Транзакция охватывает текущую попытку, профиль, receipt и нужную статистику. Выбор зафиксировать в ADR-002 с тестом поддерживаемых браузеров.

Почему не оставить независимые `localStorage.setItem`: несколько ключей не дают атомарности; BroadcastChannel сам по себе не является блокировкой; read-modify-write из двух вкладок может потерять результат. Не заявлять обратного в реализации.

- Каждая запись получает schemaVersion/revision. Транзакция сравнивает актуальную revision и применяет команду или возвращает conflict.
- Start/replace/finalize/import читают и условно обновляют общий `profileRevision + activeAttemptId` в той же IDB readwrite transaction, что и затронутые attempts/receipts/daily slots. Два start из ready не могут создать две незаметно конкурирующие активные партии.
- Reward store использует уникальный primary key `rewardKey`; daily slots — уникальный key `[language, date]`, а entryId/scheduleVersion хранятся как неизменяемые данные этого слота. Проверка отсутствия и вставка происходят внутри общей транзакции, не отдельными async read/write. Второй finalize возвращает уже committed receipt/record, а не пересчитывает grant с устаревшего snapshot.
- BroadcastChannel уведомляет остальные вкладки о commit; correctness от него не зависит. Если его нет, актуальность сверяется перед записью и при focus/visibilitychange.
- Одна активная обычная партия на профиль. Вторая вкладка показывает ту же партию; устаревший ход не создаёт новую попытку и не расходует ошибку.
- Если игрок явно заменяет активную партию, это отдельная команда abandon/start с понятным предупреждением.
- Не блокировать main thread сериализацией всей истории на каждый toggle. Selection допустимо держать transient; подтверждённые ходы сохранять.
- Prefs, consent и mute могут оставаться небольшими отдельными ключами, но иметь единственный adapter API; никакого обходного `removeItem` в session observer.
- Для extension сначала дождаться `initStorageAdapter` и прочитать действительный источник. Migration выполняется внутри соответствующего origin; web и extension не выдаются за синхронизированный профиль.
- При недоступном IndexedDB предложить временную локальную сессию с предупреждением «прогресс не сохранится», а не молча создать постоянный новый профиль.
- Не отправлять playerSeed, полную историю и snapshot сохранения в сеть.

### 4.7. Миграция без потери заработанного

**ARCH-04 / P0.** Создать versioned migration fixtures для нынешних `foldwink:stats`, `progress`, `daily`, `active-session`, `archivistProfile`, языка/темы/согласия и extension adapter.

Порядок:

1. Дождаться authoritative storage adapter. Прочитать все нужные исходные ключи, не записывая defaults.
2. Проверить JSON, типы, числа, диапазоны, длины массивов, известные enum. Не доверять spread неизвестного объекта.
3. Сохранить локальный pre-migration snapshot с версией и временем. Это backup, не отправка пользователю наружу.
4. Построить новый агрегат в памяти. Сохранить totals, cosmetics, supporter, seed, язык/тему. Исторические totals не пересчитывать из неполной истории.
5. Для известных ранее solved lineage создать legacy reward-consumed markers, чтобы migration не открыла массовый повторный XP.
6. Отдельно сохранить legacy Ink/Wax/prestige и старые grace-wax события. Не переписывать прошлый loss как win или наоборот.
7. Если старый active contract действительно содержит уже списанную положительную ставку, вернуть её в legacy Wax один раз по migration receipt; контракт закрыть с пояснением. Не выдумывать сумму при повреждённых данных.
8. Старую активную партию восстановить с legacy rules только при достаточных валидных данных. Если puzzle/version не восстановимы, сохранить snapshot для экспорта и объяснить невозможность продолжить; не подставлять другую доску с тем же ID.
9. Записать новый schema marker, состояние и migration receipt атомарно. Повторный bootstrap — no-op.
10. Исходные данные не удалять в первом совместимом выпуске. Retention/очистку backup документировать; не копить их без лимита.

Нераспознанные legacy solved IDs хранить в `unresolvedLegacySolvedRefs`. При каждом обновлении versioned ID→lineage mapping выполнять отдельный idempotent reconciliation: до допуска reward commands преобразовать вновь распознанные записи в consumed markers атомарно. Не считать bootstrap migration единственной возможностью этого сопоставления и не открывать повторный XP после появления нового mapping.

При повреждении одного optional preference допустим default только этого поля. При повреждении ядра показать восстановление/экспорт/явный сброс; не перезаписывать исходник до выбора пользователя. Clear all data должен работать через общий repository и очищать также memory cache, IndexedDB и соответствующие adapter keys, предупреждая о необратимости.

### 4.8. История и объём

Хранить компактные lifetime markers уникальных наград и коллекции; подробный журнал команд — только для активной попытки и ограниченного диагностического хвоста без личных данных. Предложенный лимит подробной истории — последние 500 попыток; агрегаты first-attempt и daily records сохраняются независимо. Ограничение configurable и тестируемое, не случайное удаление старых achievements. DailyRecord самодостаточен: `{language, date, entryId, scheduleVersion, puzzleRef, outcome, mistakesUsed, winkUsed, durationMs, attemptId, receiptId?}`; отсутствие старого подробного attempt не уничтожает результат и не меняет его идентичность.

Измерить размер профиля на 1, 100, 1000 и 10 000 завершений. Не вводить преждевременную базу из десятков object stores: необходимая атомарность важнее количества абстракций.

## 5. Баланс: управляемая кривая вместо случайного скачка

### 5.1. Из чего складывается трудность

**CONTENT-01 / P1.** Разделить минимум пять факторов: знакомство со словами, очевидность общей связи, количество правдоподобных альтернатив, культурную зависимость и полезность Tabs. Старые `editorialRank`/score не являются откалиброванной шкалой и не должны автоматически определять порядок выдачи.

В аудите диапазоны EN пересекаются: easy 4–76, medium 8–81, hard 15–70. Это не доказательство «hard легче easy», а доказательство, что текущие численные поля нельзя без проверки трактовать как единую шкалу человеческой трудности.

Целевые диапазоны для практики:

| Band | Назначение | Характер задачи | Условия входа |
|---|---|---|---|
| B0 | Первое знакомство | Бытовая лексика; ясная опорная группа; нет спорных двойных принадлежностей | Только явный starter manifest |
| B1 | Уверенное easy | Прямые категории; не более одного мягкого ложного следа | Редакторское ревью и mobile-fit |
| B2 | Первый Wink / medium | Понятные слова; одна менее очевидная связь; качественные Tabs | Ручная проверка Wink-подсказки |
| B3 | Развитый medium | Несколько типов связей; контролируемые пересечения | Пилот показывает объяснимые ошибки |
| B4 | Hard | Более необычная связь, но не недостаток знаний ради наказания | Отдельная редакторская и человеческая проверка |

Band — внутренний порядок сложности, а не новый режим или механика. В интерфейсе остаются понятные easy/medium/hard и необязательная рекомендация.

### 5.2. Стартовая последовательность

**CONTENT-02 / P1.** Для каждого языка выбрать 6 конкретных существующих задач и зафиксировать ссылки в `puzzles/manifests/starters.<lang>.json`. Не полагаться на порядок файлов, `pool[0]`, числовой ID или сортировку сборщика.

| Позиция | Задача опыта | Контентное требование |
|---|---|---|
| 1 | «Я понял и сам нашёл связь» | B0; знакомые категории; первая группа находится без подсказки |
| 2 | «Я могу сделать это ещё раз» | Другая тематика, B0/B1, без повторов слов первой доски |
| 3 | Знакомство с Wink | Первый B2; подсказка объяснима; игрок вправе отказаться |
| 4 | Закрепление | B1/B2, не новый тип трудности одновременно с длинными словами |
| 5 | Небольшой вызов | B2; один честный ложный след |
| 6 | Выход в обычную практику | Проверенный B2 или B1 по выбранной рекомендации |

Это не обязательный курс из шести экранов подряд. После каждой доски есть естественный конец сессии; daily и ручной выбор практики доступны отдельно. Для возвращающегося игрока onboarding не запускается заново из-за обновления.

На первом запуске показать два коротких интерактивных действия: выбрать четыре карточки → подтвердить группу. Игрок выполняет их сам. Skip ведёт к первой учебной доске без обучающих overlay, а не к случайному daily. Если игрок явно выбрал «Сегодняшняя задача», открыть настоящий daily и обозначить его сложность; не подменять.

### 5.3. Алгоритм следующей практической доски

**GAME-09 / P1.** Отделить `selectionSequence` от количества побед. Он увеличивается при подтверждённом выборе следующей новой доски, в том числе после поражения. Retry не увеличивает sequence и сохраняет puzzle ref, но создаёт новый attemptId.

Вход алгоритма: язык, выбранный tier, recommended band, завершённые starter positions, история показанных lineage, последние темы, selectionSequence, playerSeed, catalogVersion. Все данные подаются аргументами; функция не создаёт seed и не пишет storage.

Порядок отбора:

1. Если игрок следует стартовой дорожке, взять конкретную следующую starter entry.
2. Иначе выбрать только ready-задачи нужного языка и tier; при включённой рекомендации — текущего band.
3. Исключить уже показанные lineage, пока в допустимом диапазоне остаются новые. «Показанная» и «решённая» — разные множества.
4. Среди доступных предпочесть задачи без того же ведущего topic tag, что у последних двух досок, и с минимальными пересечениями item vocabulary с последними тремя.
5. Если фильтр разнообразия опустошил выбор — ослабить только его; не перепрыгивать скрыто в hard или другой язык.
6. Если band исчерпан — предложить соседний проверенный band того же tier либо повторение с явной надписью. Не выдавать повтор как новую задачу.
7. Стабильно отсортировать кандидатов по ID; выбрать seeded index от `catalogVersion + language + tier + band + selectionSequence + playerSeed`.
8. Зафиксировать выбор и sequence одной командой start. Reload показывает ту же задачу, а не другой random.

### 5.4. Рекомендация сложности, не скрытая подстройка

**GAME-10 / P1.** Первоначальный алгоритм — прозрачный, rule-based и консервативный:

- Рассматривать последние пять first-attempt результатов на редакционно проверенных practice-досках выбранного tier. Retry, custom, duel, mastery и Palimpsest не калибруют навык.
- После минимум пяти таких результатов, если минимум четыре победы и медиана ошибок среди побед ≤1, можно предложить следующий band. Не переводить автоматически.
- После двух последовательных first-attempt поражений можно предложить более спокойную доску или Wink-практику. Не сбрасывать накопленную коллекцию.
- Использование Wink не считается ухудшением навыка и не исключает предложение повышения.
- Время решения не является первоначальным условием повышения: язык, доступность и стиль мышления слишком сильно на него влияют.
- Ручной выбор сохраняется. Если игрок отклонил рекомендацию, не повторять её каждый ход; максимум один раз на следующие пять релевантных завершений.
- На верхнем/нижнем band соседнего перехода нет. Никакого повышения в отсутствующий RU/DE hard.

Числа «пять / четыре / две» — стартовые настройки эксперимента, не доказанные оптимумы. Хранить их в `src/game/config/balance.ts` с версией и тестами. Менять только по результатам пилота, сохраняя сравнимость когорты.

### 5.5. Честная ошибка и обратная связь

**GAME-11 / P1.** После уникальной неверной четвёрки:

- Увеличить mistakesUsed ровно на один.
- Коротко выделить выбранные карточки и дать спокойное сообщение. Не трясти весь экран, не включать красный fullscreen.
- Если существующая механика «one away» сохраняется: сообщать только математически достоверное наличие трёх элементов одной нерешённой группы; не выдавать «почти» случайно и не раскрывать, какие три.
- После feedback оставить выбранную четвёрку видимой и редактируемой; не заставлять восстанавливать гипотезу из памяти. Deselect all всегда доступен.
- Повтор этой четвёрки: «Эту комбинацию уже проверяли — измените выбор», без расхода ошибки и без misleading success sound.
- Не включать autohint после неудачи без согласия. Допустимо один раз напомнить о бесплатном Wink, если он доступен, не использовать его автоматически.

Уникальная четвёрка, отличающаяся одним item ID, — новая гипотеза и расходует ошибку, если неверна. Перестановка четырёх тех же карточек — не новая.

### 5.6. Wink и Tabs

**GAME-12 / P1.** Для medium: старт — один раскрытый символ подсказки; после каждой решённой группы — ещё один значимый символ на нерешённых tabs. Пробелы и пунктуация не расходуют этап раскрытия. Для Unicode использовать grapheme-aware обработку с тестами, а не разрезать surrogate/combining sequences.

- Успешно решённая группа: tab показывает полное название категории.
- Один Wink за попытку раскрывает **полное название выбранной категории**, не решает её и не выделяет правильные карточки.
- Wink можно использовать только на нерешённом tab. Повтор команды не расходует второй ресурс; он невозможен.
- Если редакционная короткая подсказка отличается от названия, UI и accessibility label должны различать «подсказка раскрывается» и «Wink: показать категорию».
- Easy: Tabs/Wink отсутствуют по правилам. Hard: текущий строгий вариант без Wink явно обозначен до старта; не вводить непроверенную hard-подсказку в этом проекте.
- Не обещать в комментариях или onboarding, что stage 3 обязательно раскрывает длинное слово полностью.
- После использования остаётся спокойная отметка «Wink использован». Ни красного штрафа, ни «победа с костылём».

## 6. Календарь daily и контентный pipeline

### 6.1. Неизменяемый календарь

**CONTENT-03 / P0.** `puzzles/manifests/daily.<lang>.<period>.json` содержит явные записи:

```ts
type DailyEntry = {
  entryId: string;
  date: string;                 // YYYY-MM-DD, local calendar day
  language: 'en' | 'ru' | 'de';
  puzzleId: string;
  lineageId: string;
  contentVersion: string;
  scheduleVersion: string;
};
```

- Опубликованную entry не менять при обычном обновлении пула. Расширение календаря добавляет будущие записи, а не перехеширует прошлые.
- Перед public slice подготовить минимум 30 последовательных дней для каждого выпускаемого языка. Контентная готовность языка — отдельный gate, а не «EN проверен, значит всё готово».
- Начатый daily использует дату старта до завершения после полуночи. Новый daily следующего дня можно открыть только как отдельную попытку, не пересобирая текущую.
- При смене timezone не переписывать прошлые записи. Системные часы локальны и не защищены от манипуляций; это не доверенный соревновательный сервис.
- Один дневной слот на язык хранит первый win/loss и ссылку на попытку; повтор доступен с маркировкой.
- Abandon не создаёт дневной win/loss, но остаётся записью стартовавшей попытки и не исчезает из first-start abandonment. Следующая попытка может заполнить ещё пустой daily terminal record, но не считается первым знакомством с доской. Отображение/исследование daily отличает такой результат от решения без предварительного abandon.
- Опубликованные versioned daily payloads остаются адресуемыми в статическом архиве релиза и следующих версий: GC подробной истории не удаляет серверный статический файл старой редакции. Для replay используется сохранённый PuzzleRef, а не актуальный текст того же ID. Offline replay требует закешированной версии; при отсутствии сети честно предложить загрузить позже. Нарушенную доступность старого опубликованного payload считать дефектом, не подменять новой редакцией.
- На конец горизонта: экран «Новая ежедневная задача пока недоступна» и свободная практика/архив. Не выдавать случайную персональную доску под видом daily.
- Offline: если запись известна, но контент не закеширован, объяснить именно отсутствие загрузки. Не выбирать другой ID или язык.
- Если в опубликованной доске обнаружена существенная неоднозначность: не менять начатые ответы; выпустить notice/erratum, сохранить историю и явно указать статус в архиве. Исправленную редакцию выдавать вне старого entry либо по новой будущей записи.

### 6.2. Метаданные качества

**CONTENT-04 / P1.** Отделить authoring/editorial metadata от runtime payload.

```ts
type EditorialRecord = {
  puzzleRef: PuzzleRef;
  publicTier: 'easy' | 'medium' | 'hard';
  band: 'B0' | 'B1' | 'B2' | 'B3' | 'B4' | 'unrated';
  vocabularyFamiliarity: 'common' | 'mixed' | 'specialist';
  relationTypes: string[];
  topicTags: string[];
  anchorGroupId: string | null;
  ambiguityRisk: 'low' | 'review' | 'reject';
  tabReview: 'not-applicable' | 'pending' | 'approved';
  mobileFit: 'pending' | 'approved' | 'reject';
  authorReview: { reviewerId: string; date: string } | null;
  independentReview: { reviewerId: string; date: string } | null;
  playtest: { cohortId: string; firstAttemptCount: number } | null;
  status: 'unreviewed' | 'candidate' | 'ready' | 'quarantined';
};
```

Reviewer IDs — рабочие идентификаторы редакторов, не персональные данные игроков. В runtime доставлять только необходимое: ref, текст, группы, Tabs, tier/band и компактные topic tags для локального выбора. Полные reviewer notes, rationale и отклонённые варианты не загружать на первый экран.

### 6.3. Редакторский маршрут и правила приёмки

**CONTENT-05 / P1.** Пилот — 30 EN-досок как первая исследовательская выборка, включая шесть starters и переходы B0–B4; RU/DE проходят собственный boot/calendar safety review и затем отдельную человеческую калибровку. Нельзя переносить английский win rate на другой язык.

Для каждой promoted-доски:

1. Автоматическая структура: 16/4×4, уникальность ID/текста, корректные hints, допустимые символы, ссылки manifest.
2. Автор/дизайнер выписывает ожидаемые связи и правдоподобные ложные альтернативы.
3. Независимый validator решает/разбирает задачу без подсказки автора; фиксирует спорные принадлежности.
4. Редактор принимает окончательное решение, особенно по разговорным значениям, переводам, омонимам, культурным знаниям и искусственным категориям.
5. Проверяется, что название раскрытой категории действительно объясняет все четыре слова. «Так задумал автор» не считается объяснением.
6. Tabs проверяются на полезность, совпадения первых букв и отсутствие непреднамеренного полного ответа всем категориям слишком рано.
7. Render каждого длинного слова/категории проверяется на 390 px и при увеличенном тексте.
8. Присваивается provisional band с причиной; после человеческой игры сохраняются отдельные наблюдения, не заменяемые красивой итоговой цифрой.

Не генерировать большую партию для замены предупреждений. Если board отклонена — quarantine reason + replacement one-for-one с отдельным review. Сохранять прежний файл/версию в редакционном архиве. Число активных задач не сокращать случайно; качество curated entry points повышать отдельно от полного legacy pool.

`validate` должен поддерживать отчёт по severity и изменённым доскам: новые fatal errors блокируют сборку; legacy advisory имеет baseline и владельца. Стартовые и calendar entries не принимаются с unresolved ambiguity/Tab/mobile blockers. Не требовать «ноль повторов слов во всех 3000» — это неподходящий критерий качества.

## 7. Награды, коллекция и причины вернуться

### 7.1. Простая экономика

**GAME-13 / P0–P1.** Предлагаемая версия reward policy v2:

- 80 XP за первую победу над официальной lineage в разрешённом контексте. Значение конфигурируемое, косметическое, одинаковое с Wink и без.
- `unique-solve:<language>:<lineageId>` — общий ключ между practice, zen, archive, onboarding и первой попыткой daily. Content typo-version не создаёт новый XP.
- Повторный показ result, новая retry attempt, другой режим и изменение сортировки не дают повторный XP.
- Loss и abandoned не дают XP. XP не отнимается.
- Ink/Wax/prestige остаются read-only историей; новые grants/spending и автоматическая grace-защита отключаются новой policy. Старые сохранённые события остаются.
- Не вводить exchange rate, расходники или новую валюту, чтобы искусственно оправдать старые counters.
- Существующие уровни и cosmetics сохраняются. Новые уровни считаются через одну versioned функцию, без потери уже открытого; если пороги меняются — migration с отдельным тестом.

### 7.2. Матрица eligibility

| Событие | Lifetime basic stats | Daily record | Unique-solve XP | Collection / mastery |
|---|---|---|---|---|
| Первый daily win | Да, отдельно помеченный контекст | Записать первый исход | Да, если lineage ещё не rewarded | Daily completion + unique solve |
| Первый daily loss | Да | Записать loss | Нет | Daily participation completion, без знака победы |
| Replay daily после любого исхода | Replay history, не повтор lifetime scored total | Не изменять | Нет | Не повторять дневную отметку |
| Practice/Zen/Archive первый win этой lineage | Контекстная статистика; calibration только practice first attempt | Нет | Да, если eligible key отсутствует | Unique solve |
| Practice retry win после loss | Retry stats; исход first attempt не переписывать | Нет | Да, один раз за первую фактическую победу lineage | Unique solve |
| Повтор уже rewarded lineage | Replay stats | Нет | Нет | Только просмотр существующей отметки |
| Mastery win | Отдельная mastery statistic | Нет | Нет дополнительного XP; основной unique solve разрешён один раз, если официальный board ещё не rewarded | Badge один раз по lineage + rules version |
| Duel / Custom | Только собственная история этого контекста | Нет | Нет | Нет основной коллекционной награды |
| Palimpsest первое завершение по правилам | Отдельно | Нет | Нет новой валюты/XP в v2 | Один специальный stamp |

Для daily после первого loss игрок может честно решить ту же доску в practice и получить ещё не выданный unique-solve XP; daily record остаётся loss. Это не фарм: один общий lineage key. В интерфейсе не предлагать обход как «спасти daily».

Переименование/перевод одной задачи: language входит в ключ, поскольку словесная задача другого языка может реально отличаться; UI не обещает глобальную межъязыковую уникальность. Старые solved IDs нормализовать в язык/lineage через manifest, неизвестные IDs сохранять legacy без угадывания.

### 7.3. Детерминированная коллекция

**UX-01 / P1.** Две понятные линии коллекции, не две валюты:

1. **Решённые страницы:** отметки за 1, 5, 10, 25, 50, 100 уникальных решённых задач; далее только заранее подготовленные ступени. Условия видны.
2. **Ежедневные страницы:** календарные отметки за участие и завершение daily, где win/loss визуально различимы. Пропуск дня оставляет пустой день, не обнуляет коллекцию.

Старые stamps сохраняются отдельным блоком «Ранняя коллекция», без необходимости переигрывать ради возврата. Случайные 45%-дропы заменить объявленными условиями. Первый новый stamp показать inline на результате; просмотр крупной иллюстрации добровольный.

Опциональные mastery факты: flawless, without Wink, challenge cleared. Они не формируют унизительную итоговую оценку и не уменьшают награду обычной победы. Ни badge «правильный игрок» против «игрок с подсказкой», ни cash-like визуал ставок.

### 7.4. Игровые hooks и проверяемые гипотезы

| Hook | Реализация | Как проверить | Что исключено |
|---|---|---|---|
| Первая найденная связь | Выверенная опорная группа в starter | Время до первой группы + пересказ правил игроком | Автоматически решить за него и считать вовлечением |
| «Теперь вижу закономерность» | Честный reveal категории и короткое объяснение на result | Игрок может объяснить, почему четыре слова вместе | Непонятные авторские категории |
| Агентность Wink | Раннее знакомство, один свободный выбор tab | Игрок знает, что действие бесплатно и не решает группу само | Платный/стыдный hint |
| «Ещё одну, но другую» | Одно primary Next, тематическое разнообразие | Доля добровольного следующего старта после result | Модалка перед Next, бесконечный autoplay |
| Завтрашний ритуал | Общий daily и видимая дата | Органическое возвращение в следующие дни | Потеря валюты/прогресса за отсутствие |
| Личная история | Детеминированные страницы и старые achievements | Игрок понимает следующий достижимый milestone | Lootbox и случайный обязательный конверт |
| Дружеское сравнение | Один понятный share/challenge sheet | Доля действительно завершённых share actions | Фальшивый leaderboard или «друг лучше вас» без доказательств |

Автоматический переход в следующую игру запрещён. Продолжение должно быть добровольным; хороший короткий выход после результата — часть качества, а не ошибка удержания.

## 8. Визуальная концепция: Paper Theatre

### 8.1. Что означает «кардинально улучшить»

**UX-02 / P1.** Изменить не только цвета, а четыре вещи одновременно: композицию первого экрана, читаемость поля, материальность карточек и характер перехода «четыре карточки → найденная группа». Сохранить минимализм, но придать игре собственный узнаваемый образ.

Образ: небольшой стол для бумажной головоломки; тёплая поверхность, чёткая типографика, аккуратно согнутые края, печати коллекции. Карточки выглядят предметами одного набора, а не разными виджетами dashboard. Фон статичный, спокойный; цвет и движение подчёркивают действие игрока.

В первом design slice сравнить текущий и новый Menu → Game → Result при одинаковой задаче и viewport. Критерий успеха — не количество эффектов, а ясный primary action, читаемые слова, привлекательность и понятность состояний.

### 8.2. Дизайн-токены

Создать один источник токенов `src/styles/tokens.css` либо согласовать существующий эквивалент; Tailwind utilities должны ссылаться на него. Motion tokens — в одном модуле `src/styles/motion.ts`, CSS custom properties генерируются/экспортируются без ручных расходящихся копий.

| Token group | Предлагаемое начало | Проверка |
|---|---|---|
| Paper / surface | `#F5EFE3` / `#FFFCF5` | Не использовать текстуру, снижающую контраст под словами |
| Ink / muted | `#252A32` / `#62646B` | Контраст каждой реальной пары, включая disabled/helper text |
| Accent / Wink | Тёмный teal `#21665F`, тёплый amber как supporting accent | Accent не означает одновременно warning и selected |
| Solved groups | Четыре приглушённых различимых tint с отдельным контрастным текстом | Цвет дополняется label/иконкой; проверка при нарушении цветоразличения |
| Spacing | 4, 8, 12, 16, 24, 32, 48 px | Удалить случайные одноразовые отступы без причины |
| Corners | Card 10–14 px; panel 18–24 px | Не превращать каждый элемент в огромную pill |
| Shadows | Один контактный + один мягкий слой для активного объекта | Не многослойное неоновое свечение всей доски |
| Focus | Видимое контрастное кольцо с offset | Не обрезается overflow контейнером |

Цвета — стартовая спецификация направления, **не утверждение об уже измеренном контрасте**. При реализации обычный текст должен выдерживать не менее 4.5:1, крупный — 3:1; значимые границы/focus — не менее 3:1 к соседнему цвету. Измерить, зафиксировать пары и при необходимости скорректировать hex до приёмки.

Типографика:

- Основной текст и слова карточек: локально поставляемый Manrope, 500–700 по функции; наборы кириллицы/латиницы проверены.
- Фирменный заголовочный шрифт: OPTIONAL один дополнительный serif после side-by-side сравнения двух кандидатов и проверки лицензии/кириллицы/немецких знаков. Если выразительность достаточна текущим шрифтом — не подключать новый.
- На мобиле card text ориентир 14–16 px, line-height 1.15–1.25; helper 12–14 px; action 15–16 px. Не снижать слова до 10–11 px ради помещаемости.
- Длинные слова не обрезать ellipsis: это меняет саму головоломку. Допускаются редакторская замена или разумные переносы, но не скрытие частей ответа.
- Шрифт не должен скачивать Google Fonts при первом запуске. Проверить fallback и layout shift при холодном кеше.

Существующие темы сохранить в settings. Новая основная светлая и тёмная темы должны быть полностью специфицированы; legacy темы адаптировать через token mapping. Не удалить пользовательскую тему из сохранения, если она не участвует в первой демонстрации.

### 8.3. Размеры и responsive contract

**UX-03 / P1.** Основные контрольные размеры: desktop 1440×900, tablet 1024×768, mobile 390×844, zoom 100%, device scale factor зафиксирован в evidence. Дополнительно 320 px, 430 px, landscape/короткая высота и 200% browser zoom.

| Зона | Mobile 390 | Tablet / Desktop | Поведение при недостатке места |
|---|---|---|---|
| Page padding | 12 px по сторонам, safe areas добавочно | 24–32 px | Не компенсировать нехватку места уменьшением всех controls |
| Game column | Доступная ширина, без горизонтального scroll | Max-width ориентир 640–720 px | Центрировать колонку, а не растягивать карточки на весь монитор |
| Grid | 4 равных колонки; gap 6–8 px | Gap 10–12 px | Четыре колонки сохраняются; длинный текст проверять редакционно |
| Cards | Базовая min-height 68–76 px | Ориентир 84–104 px | Высота может расти при увеличенном тексте; вертикальный scroll допустим |
| Tap targets | ≥44×44 px для самостоятельных actions | Те же функциональные пределы | Малый icon имеет большой доступный hit area |
| Tabs | Четыре равных slot, текст переносится | Согласованы с шириной поля | Раскрытый label не перекрывает соседний tab |
| Controls | Submit primary; Shuffle/Deselect вторичные | В пределах игровой колонки | Sticky footer только с зарезервированным местом и safe-area padding |
| Result CTA | Next/Practice первым в композиции | Не теряется среди share/supporter | Доступен без открытия коллекционного modal |

Размер карточки не фиксировать одновременно невозможными width/height/viewport ограничениями. Например, при 390 px сначала вычислить доступную ширину после page/mat padding и gaps; фактическую карточку проверить скриншотом с длинным словом, а не только DOM rectangle.

Устранить общий media query, который принимает любой телефон уже 400 px за extension и сжимает карточки до 52 px. Compact embed layout включается явным host/display-mode признаком, а не одной шириной. `safe-area-inset-bottom` не перекрывается компактным правилом `.25rem`.

На обычном mobile viewport базовая easy/medium игра должна показывать главный статус, поле и Submit без неуместной пустоты или перекрытия. При 200% zoom приоритет — доступность текста и вертикальная прокрутка; не обещать невозможное помещение всего в один экран.

### 9.2. Practice picker

Показывает recommended next и ручной выбор easy/medium/доступного hard. У каждой опции короткое объяснение правил. Zen — переключение спокойного представления или отдельный вложенный entry с теми же ясными правилами. Mastery — дополнительное испытание ниже основной практики, после знакомства с medium, но не платная/валютная разблокировка.

Рекомендация формулируется «Попробовать чуть сложнее?» или «Выбрать более спокойную задачу?», без диагноза навыка и давления. Уровни существующего игрока не закрываются заново; новичок также может выбрать доступный tier после предупреждения о сложности.

### 9.3. Game

**UX-05 / P1.** Иерархия: mode/date → remaining mistakes → Tabs (если есть) → solved groups + 4×4 remaining grid → feedback line → controls. Timer по умолчанию не главный элемент; в Zen скрыт, в остальных доступен по настройке.

Обязательные states карточки: default, hover только при hover-capable input, pressed, selected, keyboard-focused, incorrect feedback, moving into solved group, disabled-terminal. Selected определяется не только цветом: border/mark + `aria-pressed`.

Поведение:

- Toggle карточки — button, Enter/Space; корректный focus ring.
- Пятый выбор не вытесняет скрыто первый: показать «Выберите только четыре» без ошибки.
- Submit disabled до четырёх, с понятным сообщением `Выбрано N из 4`; busy состояние на commit не теряет focus.
- Shuffle меняет только порядок нерешённых карточек; выбранные item IDs и неправильные signatures сохраняются.
- Deselect очищает выбор, не историю guesses.
- При правильной группе карточки собираются в solved strip с названием и четырьмя словами. После движения клавиатурный focus переводится на первый оставшийся элемент либо result heading в terminal-состоянии; он не исчезает в удалённом DOM.
- Последняя четвёрка требует явного Submit по текущим правилам. Не добавлять автопобеду как побочный эффект анимации.
- Feedback имеет спокойный `aria-live=polite`; не зачитывать весь grid после каждого toggle.
- Выход из игры сохраняет попытку. Browser Back и мобильный swipe-back не должны терять прогресс без предупреждения.

### 9.4. Result: победа

**UX-06 / P1.** Экран читает immutable completion/receipt. Состав:

1. Короткий итог: «Решено»; название режима/дата.
2. Четыре собранные группы с раскрываемым объяснением связей. Слова видны без отдельной загадочной анимации.
3. Факты: ошибки, Wink, optional time; без итоговой унизительной grade за Wink.
4. Inline награда: `+80 XP` только если выдана; иначе понятное «Повтор — прогресс уже учтён». Новая stamp компактно, с optional «Рассмотреть».
5. Один primary CTA: после daily — «Ещё одна задача»; после practice — «Следующая задача». Не автозапуск.
6. Вторичные: Поделиться; Коллекция; На главную.
7. Tip/supporter — тихо ниже основных действий и только при валидной конфигурации, не поверх результата.

Ни конверт, ни sound tail, ни supporter message не должны блокировать Next. Итог всегда можно перечитать; закрытие вкладки не лишает награды.

### 9.5. Result: поражение

**UX-07 / P1.** Показать найденные и пропущенные группы с объяснением, оставляя чувство понятности, а не «игра решила иначе». Тон нейтральный: «На сегодня эта задача не сложилась» для daily; «Попробуем ещё?» для practice.

- Два различимых действия: «Повторить эту задачу» и «Другая задача». Первое не обещает новый daily record/награду; второе выбирает новый puzzle ID при наличии новых кандидатов.
- Для daily первым предложить практику; повтор остаётся доступным, но помечен.
- Показать использованный/неиспользованный Wink как факт, без упрёка.
- Inline feedback «Была ли связь спорной?» — optional локальная отметка/экспорт для пилота; не отправка текста автоматически.
- Не предлагать оплатить, посмотреть рекламу ради дополнительных жизней или потратить Wax для спасения результата.

### 9.6. Collection / Stats

**UX-08 / P2.** Collection показывает earned stamps и ближайшее детерминированное условие. Stats различают daily, first-attempt practice, retries и legacy totals. Нельзя переименовать старый общий win rate в «первый заход», если данных для этого нет.

Структура: progress summary → коллекция страниц → раскрываемая статистика → legacy history. Streak, если сохранён, вторичен и не обещает бессрочную защиту. «Не пропусти, иначе потеряешь» отсутствует.

Settings доступны отдельно: язык, тема, звук, haptics, reduced motion override, optional timer, privacy/consent, local backup/import, clear data, About. Изменение языка не изменяет активную attempt; предложить завершить текущую или начать отдельную в другом языке.

### 9.7. Dialog / sheet contract

**UX-09 / P1.** Все settings, share, collection detail, onboarding help, transfer preview и mastery explanation используют одну доступную оболочку Dialog. На mobile она может выглядеть как bottom sheet, но иметь те же keyboard/ARIA правила.

- Role dialog, accessible title, description при необходимости, inert background, focus containment.
- Escape и видимая Close; возврат focus к trigger. Если trigger исчез, разумный fallback heading/action.
- При критическом подтверждении импорта/сброса initial focus не на destructive action.
- Нельзя вложить бесконечный стек разных modal; максимум один основной sheet + осмысленный alert confirmation.
- Outside click не должен уничтожить несохранённый редактируемый import input; подтвердить или сохранить draft.
- Для длинного содержимого внутренний scroll, без закрывающей кнопку клавиатурой и без прокрутки фонового grid.

## 10. Движение, иллюстрации и звук

### 10.1. Motion specification

**UX-10 / P1–P2.** Целевые диапазоны, подлежащие проверке на устройстве:

| Событие | Нормальный motion | Reduced motion |
|---|---|---|
| Card press | 80–120 ms, небольшое изменение положения/тени | Цвет/граница без перемещения |
| Select | 100–160 ms, лёгкий подъём ≤2 px | Мгновенное выбранное состояние |
| Deal | 180–280 ms, небольшой stagger, суммарно ≤450 ms | Сразу полный grid, без ожидания |
| Incorrect | 140–220 ms, локальное выделение | Статичный feedback + текст |
| Group solve | 350–500 ms: собрать четвёрку в бумажный strip | Короткий fade ≤100 ms либо мгновенный layout |
| Wink | 180–260 ms, раскрытие tab | Сразу текст + announcement |
| Result transition | 200–350 ms | Смена без пространственного перемещения |
| Stamp reveal | ≤700 ms, можно пропустить | Сразу готовая отметка |

От terminal commit до доступного Next — не более 700 ms в обычном режиме и без искусственной задержки при reduced motion. Это внутренний критерий UX, не измеренный текущий результат.

Технические требования:

- У трансформации один владелец. Layout movement и press/fold transforms размещаются на разных вложенных элементах либо управляются одной системой.
- Удалить бесконечный `requestAnimationFrame`, когда карточка покоится. Возврат к нулю завершается epsilon-threshold и cancelAnimationFrame.
- Удалить/централизовать 16 параллельных gyro listeners; по умолчанию gyro выключен. Не запрашивать sensor permission автоматически.
- При reduced motion отключаются JS-движение, particles, gyro и CSS deal; недостаточно одной неполной media query.
- Все таймеры/listeners/animation handles очищаются при unmount, restart и language switch.
- Быстрые clicks, Shuffle во время перехода, уход в background и возврат не оставляют ghost cards и не ломают focus.
- В hidden tab не работают декоративные циклы. Аудио и таймер активного размышления приостанавливаются по определённой политике.

### 10.2. Asset specification

**UX-11 / P2.** Подготовить небольшой исходный набор:

- Один логотип/wordmark и mono fallback; один язык формы, не три разные айдентики.
- 8–12 собственных SVG-иконок: settings, sound, share, back, shuffle, clear, Wink, collection, check/error и install при необходимости.
- Один лёгкий tileable paper texture, отдельный clean fallback. Текстура декоративная, не несёт смысл.
- Шесть milestone stamps для начала + адаптация существующих earned stamps; каждый имеет ID, label, SVG/raster fallback и license/source record.
- Светлая/тёмная cover-композиция для share, без скачивания сторонних тяжёлых картинок в runtime.

AI-генерация и Figma допустимы как offline authoring-инструменты при отдельном исполнении дизайнерской задачи. Generated bitmap не заменяет читаемый HTML-текст карточек. Перед использованием ассета проверить права, артефакты, читаемость на малом размере и размеры файла; source/license записать в `assets/ASSET_REGISTER.md` либо существующий эквивалент.

### 10.3. Единый звук и haptics

**UX-12 / P2.** Публичные вызовы проходят через `useSound`/`useFeedback`. Внутри один AudioContext/mixer для процедурных и статических слоёв; двойная система mute/unlock удаляется.

| Событие | Характер | Ограничение |
|---|---|---|
| Select / deselect | Тихое касание бумаги/дерева | Rate limit быстрых taps; не громче solve |
| Submit incorrect | Мягкий сухой щелчок | Без наказательного громкого buzzer |
| Solve group | Короткая сборка/шелест | Один committed event → один звук |
| Wink | Лёгкое раскрытие сгиба | Отличим от solve, но не перегружен |
| Win | Короткая завершённая фраза | Основная часть ориентир 0.7–1.2 s; tail не задерживает UI |
| Collection | Негромкая печать | Только когда действительно новая отметка |

- Resume AudioContext только после пользовательского жеста, обработать rejected promise.
- Mute сохраняется, выключает текущие хвосты и будущие звуки; настройка не зависит от конкретного экрана.
- Haptics отдельно opt-in/настройка; отсутствие API — безопасный no-op. Звук off не обязан означать haptics on.
- Не увеличивать громкость из-за наложения нескольких win/modal sounds.
- Проверить реальные мобильные браузеры, фон/возврат, заблокированное audio, bluetooth/headphones при доступности; desktop unit test не доказывает mobile audio.
- `audio:check` и реестр происхождения ассетов обязательны. Sound pack не несёт смысловой информации, отсутствующей в интерфейсе.

## 11. Сторонние инструменты и библиотеки

### 11.1. Решение по каждой зависимости

| Инструмент | Статус | Использование | Условие принятия |
|---|---|---|---|
| Radix Dialog | Рекомендуемый узкий runtime-кандидат | Единый dialog/sheet foundation | Совместимость с React 18, styled wrapper, keyboard/reader checks; не весь UI kit |
| Vite PWA + Workbox | Рекомендуемый build/runtime-кандидат | Генерируемый asset precache и контролируемое обновление | Совместимость с текущим Vite, base path, offline/update tests |
| Nayuki QR generator | Рекомендуемая замена ограниченного QR-кода | QR для существующего share/transfer | Capacity/error tests, лицензия/notice, decoder roundtrip |
| Motion for React | Conditional | Только замена ручного layout/exit lifecycle | ADR, сравнение CSS, removal старого FLIP, bundle/interaction evidence |
| Rive | OPTIONAL / P3 | Небольшая самостоятельная фирменная сцена | Не нужен для игры; статичный fallback; не входит в первые public gates |
| Figma | OPTIONAL authoring | Прототипы и дизайн-компоненты | Не runtime; работа возможна и локально без нового платного сервиса |
| Playwright + axe integration | Dev-only оценка | E2E/автоматические a11y checks | Не заменяет ручной keyboard и screenshot QA |
| Three / Pixi / Phaser / Unity | Не подключать | Для 16 DOM-карточек не требуется | Отдельный будущий продуктовый запрос, не это ТЗ |

Radix документирует управление focus и modal semantics; это основание выбрать primitives вместо нового собственного focus trap, но качество конкретного wrapper всё равно проверяется. [Официальная документация Dialog](https://www.radix-ui.com/primitives/docs/components/dialog).

Motion поддерживает layout-анимации; это кандидат на замену текущего ручного FLIP, а не доказательство, что библиотека сама улучшит продукт или всегда уменьшит код/вес. [Официальная документация layout animations](https://motion.dev/docs/react-layout-animations).

Vite PWA описывает генерируемый precache на основе Workbox. Проектные исключения, языковые чанки и update flow необходимо настроить и проверить отдельно. [Официальное руководство precache](https://vite-pwa-org.netlify.app/guide/service-worker-precache).

Nayuki предоставляет генератор QR, включая TypeScript/JavaScript и поддержку разных размеров/ECC. Это не означает бесконечную вместимость: bounds и понятная ошибка остаются обязанностью приложения. [Страница проекта и лицензии](https://www.nayuki.io/page/qr-code-generator-library).

### 11.2. Dependency acceptance gate

**OPS-01 / P1–P2.** До каждого подключения записать: точное имя пакета и зафиксированную версию, React/Vite/TS compatibility, лицензию и notices, maintenance/security status на дату установки, compressed bundle delta, заменяемый код, fallback, способ удаления.

Не ставить `latest` без lockfile review. Не обновлять одновременно React/Vite/TS и игровой движок ради удобства библиотеки. Если выбранная версия требует upgrade стека — отдельный совместимый этап с rollback; минимальный продуктовый путь должен оставаться доступен.

Motion spike: одна solved-group анимация + Shuffle + interruption + reduced motion, одинаковый сценарий в CSS и Motion. Выбрать Motion только если измеримо уменьшает собственную сложность или исправляет воспроизводимый дефект без нарушения perf budget. Если нет — оставить CSS и закрыть эксперимент отчётом, а не тянуть его в релиз.

Никакой установки платного plugin или отправки исходников внешнему сервису «на всякий случай». Инструменты здесь — варианты реализации, а не выполненные подключения.

## 12. Share, challenge, QR и перенос профиля

### 12.1. Один share sheet

**UX-13 / P2.** На результате одна кнопка «Поделиться», открывающая варианты:

1. Текст результата без ответов.
2. Ссылка на эту задачу/дружеский вызов с явным режимом.
3. Картинка: квадрат 1080×1080 или Story 1080×1920, выбранный формат внутри одного sheet.

Share card — авторский canvas, без новой графической зависимости: frame, brand, дата/режим/язык, 4×4 абстрактная схема попыток, результат и небольшой CTA/domain. Ответы и названия категорий по умолчанию не попадают в карточку. Пользовательские имена/произвольный текст не добавлять из непроверенного URL.

Preview должен совпадать с exported blob; шрифты загружены до canvas draw, текст не обрезается, есть корректный fallback без custom font. Проверить длинные локализованные строки и разные outcomes, в том числе loss/replay/Wink. Result card не должна выдавать replay за новый daily win.

Native share:

- Проверить capability отдельно для text/url и files.
- Успешное завершение API — share action completed, но не доказательство фактического просмотра другом.
- Cancel/Abort — нейтрально закрыть; не копировать в clipboard без просьбы.
- При реальной ошибке предложить видимые «Скопировать ссылку»/«Скачать изображение».
- Сообщать «Скопировано» только после успешного clipboard write. В denied context дать ручное копирование.

### 12.2. Формат challenge/link

**ARCH-05 / P1–P2.** Versioned discriminated payload, не сериализованный ActiveGame:

```ts
type ChallengePayloadV2 = {
  v: 2;
  kind: 'official-challenge';
  puzzle: PuzzleRef;
  rulesVersion: number;
  creatorResult?: {
    result: 'win' | 'loss';
    mistakesUsed: number;
    winkUsed: boolean;
    durationBucket?: string;
  };
};
```

Official challenge по возможности передаёт ref, а не ответы. Приложение всё равно клиентское: скрыть решение от мотивированного читателя кода невозможно; не позиционировать это как защищённое соревнование.

- Canonical URL строится из конфигурации origin/base path; `/foldwink/` не теряется при копировании, SW navigation или native оболочке.
- Входные поля проверяются whitelist schema, целыми диапазонами и ограничением длины. HTML не исполняется; labels выводятся как текст.
- Неизвестная версия/board/rules → понятный экран, кнопка в обычную игру. Не crash и не fallback на случайный puzzle.
- Imported challenge не может установить supporter, profile XP, consent или daily eligibility.
- Creator result показывается как присланный результат, не серверно проверенный рекорд.
- Для существующего custom puzzle link отдельная schema с жёсткой проверкой 16/4×4, строк и суммарного UTF-8 размера. Не расширять функциональность editor этим ТЗ.

### 12.3. QR и bounded input

**OPS-02 / P2.** QR generator выбирает допустимую version/ECC либо возвращает типизированный `payload-too-large`. Не обрезать payload и не выдавать неполный QR как успешный.

Стартовые технические лимиты:

- Share/challenge URL: целевой UTF-8 budget ≤1800 bytes; при превышении предложить текстовую ссылку/файл в разрешённом формате, не обещать читаемый QR.
- QR: ECC M, версия по capacity; визуальная приёмка ограничивает итоговую плотность. Даже укладывающийся в стандарт код может оказаться непригодным на маленьком экране.
- Custom board payload после декодирования ≤32 KiB; строка item ≤120 graphemes до редакционных более строгих правил; категории ≤160 graphemes. Это защитные пределы parser, не разрешение создавать длинные мобильные слова.
- Backup file: ≤2 MiB decoded, до 500 подробных attempt records и до 20 000 компактных identity markers; реальные данные сериализации проверить на эти пределы. При достижении лимита не терять данные — предложить безопасный архивный export, а не молча урезать профиль.
- Если используется compression: проверять размер до и после распаковки, неизвестные enum и глубину структуры. Не вводить compression только ради чрезмерно большого QR.

Код должен сканироваться настоящей камерой с другого устройства при заданном размере; минимум Android/iPhone при доступности. Отсутствие устройства — явный deferred gate. Проверить quiet zone, contrast, resizing, screenshots и dark theme. Generator unit test без независимого decoder roundtrip недостаточен.

### 12.4. Backup/import и legacy transfer

**ARCH-06 / P0–P2.** Полный перенос прогресса — локальный versioned JSON-файл. QR остаётся для компактной ссылки/legacy transfer, не обещает вмещать полную историю. Старый QR, переносящий только seed/часть профиля, должен быть именно так подписан.

Перед import: parse → validate → summary preview → выбор merge/replace → локальный backup → atomic commit → перечитать UI. Preview показывает язык/версию, количество solved/daily/collection records и какие данные будут заменены. Отмена ничего не меняет.

- Merge объединяет consumed reward keys/collection identities множествами. Lifetime totals не складываются вслепую: для новой модели пересчитываются из уникальных records там, где они полны; неполные legacy totals сохраняются отдельным выбранным базовым snapshot, без притворной точности. При двух разных legacy baselines preview требует явного выбора источника: default — текущий локальный, альтернативный — импортированный. Показать обе суммы и что не войдёт в итог; не брать максимум/сумму молча. Выбор применяется ко всему согласованному legacy baseline, а уникальные новые receipts/markers объединяются независимо.
- При конфликте одного daily entry с разными исходами default — оставить текущую локальную запись; preview сообщает конфликт. Replace может применить импортированный snapshot как явное действие, но не суммировать награды.
- Импорт старой схемы проходит те же migration rules и не возвращает закрытый wager.
- Full replace не суммирует XP. В обычном merge XP строится из уникальных receipts плюс один legacy baseline, не из суммы двух профилей.
- Backup не содержит credentials, cookies, сторонние checkout secrets, email или consent чужого устройства. Privacy preference при import не включает network tracking автоматически.
- Не обещать античит: владелец local-first приложения может изменить данные или сбросить профиль. Гарантия — отсутствие случайного дублирования штатными сценариями, а не защита от хозяина устройства.

## 13. Загрузка, performance и PWA

### 13.1. Доставка контента

**OPS-03 / P1–P2.** Текущий runtime отделить от редакционной базы:

- Первый shell не импортирует весь EN-пул независимо от выбранного языка.
- Загрузить настройки/язык → компактный manifest → только нужные starter/daily/practice chunks.
- Паковать ориентировочно по 20–50 досок в статический chunk; окончательный размер выбрать по фактическим gzip/network measurements, а не сделать 1000 HTTP-запросов.
- Collection detail, QR/import tooling, Palimpsest и share-image code допускают lazy loading после основного пути.
- Не удалять данные из authoring JSON ради runtime размера: build step производит отдельный stripped payload.
- Чанк содержит version/hash в manifest. Hash — проверка целостности/соответствия, не подпись доверенного источника.
- Не загружать все три языка в фоне без явной пользы/желания пользователя. Prefetch только ближайшей логично ожидаемой доски и bounded daily horizon.
- Network/cache error не должен приводить к пустому store или навсегда disabled кнопке; retry и offline alternatives имеют тесты.

### 13.2. Измеряемые бюджеты

**OPS-04 / P2.** Стартовые внутренние цели; это не заявление о нынешней скорости и не гарантия на любом телефоне:

| Метрика | Цель public slice | Как измерять |
|---|---|---|
| Начальный JS + нужный puzzle payload | ≤250 KiB gzip суммарно | Production build + реально востребованные ресурсы холодного первого запуска выбранного языка; не сумма всех dist chunks |
| CSS | ≤25 KiB gzip | Build report и network |
| Первые fonts + декоративные raster assets | ≤180 KiB перед готовностью первой доски | Network waterfall; не включать необязательный share export |
| Визуальная стабильность | CLS ≤0.1 в сценарии начала игры | Production preview, фиксированные условия и повторные прогоны |
| Основная отрисовка | LCP ≤2.5 s на выбранном тестовом профиле | Профиль сети/CPU, браузер, median и худшие прогоны записаны |
| Ответ на игровой input | p95 локальной задержки action→visible feedback ≤100 ms без искусственного ожидания сети | Performance marks, mobile device, нагрузочный сценарий |
| Idle | Нет непрерывного декоративного rAF на спокойном поле | Performance trace 30 s после завершения переходов |
| Finish interaction | Next доступен ≤700 ms после terminal commit | E2E timestamps + визуальное наблюдение |

Не подменять реальное устройство чужой аппаратной конфигурацией. Если используется компьютер Владимира для mobile simulation, записать, что это эмуляция, а не реальный Android. При недоступности целевого телефона real-device gate остаётся открытым.

Если бюджет не выдержан — определить самые дорогие chunks и feature import, убрать необязательные эффекты/раннюю загрузку. Не ухудшать читабельность изображений/шрифтов до неприемлемого уровня ради красивой цифры.

### 13.3. Service worker

**OPS-05 / P2.** Заменить ручной precache только HTML/icons на build-generated manifest с корректным base path и политикой обновления.

- Core HTML/JS/CSS/fonts + boot content должны быть доступны offline после подтверждённой установки кеша.
- Для языка пользователя загрузить ближайшие 7 daily entries, если доступны в 30-дневном опубликованном календаре, и starter pack. Это bounded offline horizon, не обещание бесконечного offline daily.
- Остальные языки/архив — on demand; уже загруженные pinned активные доски сохраняются.
- Network navigation fallback возвращает shell только для соответствующего app path, не превращает ошибку asset fetch в HTML вместо JS.
- Новая версия SW сообщает «Обновление готово» на menu/result. Активную партию не перезагружать; versioned snapshot остаётся доступным.
- Old clients не должны писать несовместимую новую schema; schema compatibility проверяется до старта write-capable UI.
- Старые кеши чистятся по явной version policy после переключения клиентов и сохранения pinned active content. Не удалять всё на install.
- В offline меню видны только реально доступные задачи либо честно disabled entries с причиной.
- Закрытие/повторное открытие установленной PWA offline проверяется отдельно от выключения сети в уже прогретой вкладке.

### 13.4. Локальное время и жизненный цикл

**ARCH-07 / P1.** Хранить raw elapsed и active thinking time раздельно. Для исследований основное duration — сумма foreground-интервалов без modal/tutorial пауз, если они исключены определением метрики. Policy version фиксируется.

- Runtime elapsed считать монотонными часами; persisted accumulators восстанавливать после reload без использования старого `performance.now` как нового абсолютного времени.
- При visibilitychange/background сохранять накопленный интервал, не оставлять бесконечный timer/rAF.
- Системные часы назад не дают отрицательную duration. Длинный gap после crash/reload не объявлять временем активного решения.
- Raw timestamps нужны для локальной даты/восстановления, но не отправляются в аналитике с избыточной точностью.
- Timer presentation не влияет на scoring: в базовой игре нет бонуса за скорость и наказания за паузу.

## 14. Измерение баланса и возвращаемости

### 14.1. Два разных источника доказательств

**GAME-14 / P1.** Автотесты доказывают, что правила исполняются. Люди показывают, понятно ли им, интересно ли и справедливо ли. Система не считается откалиброванной только по bot solves с известными ответами.

Проводить два этапа:

1. **Наблюдаемый usability/balance pilot:** 20–30 участников целевой аудитории для качественной диагностики первой сессии. Начать с EN; для RU/DE отдельные участники с соответствующим языком. Число не обещает статистическую мощность A/B или достоверный D7.
2. **Возвращаемость:** добровольная последующая игра в течение минимум семи полных дней наблюдения после входа. Назначенные исследователем визиты и напоминания маркируются отдельно; нельзя выдавать их за organic retention.

Набор участников, их согласие, возможное вознаграждение и внешние сообщения требуют реальной организации; код сам не обеспечивает этот этап. До появления данных численные цели — гипотезы.

### 14.2. Метрики с определениями

| Метрика | Числитель / знаменатель | Сегментация / риск |
|---|---|---|
| Onboarding completion | Завершили два действия / начали interactive onboarding | Skip считать отдельно, не скрывать в отказах |
| First-group success | Нашли первую группу / начали starter | Только first encounter, без ответов исследователя |
| First-group time | Foreground время до первой правильной группы | Median, p75 и число наблюдений; отдельно abandon |
| First-board win | First-attempt wins / first-attempt terminal outcomes | Рядом показывать abandon/start, чтобы не завысить успех исключением ушедших |
| Retry recovery | Победили при retry / начали retry после loss | Не подмешивать в first-attempt win rate |
| Voluntary next | Начали другую доску после result / увидели result с доступным next | Win/loss раздельно; replay и different-board раздельно |
| Wink understanding | Правильно объяснили действие / опрошенные, увидевшие Wink | Использование само по себе не равно пониманию |
| Ambiguity signal | Независимые обоснованные жалобы / участники данной board | Малые N, язык, knowledge gap против реально двойного ответа |
| D1 / D7 | Игроки исходной когорты с qualified session на локальный день +1/+7 / когорта с полным доступным окном наблюдения | Не агрегат сырых events; locale/version/consent и organic vs invited раздельно |
| Share completion | Завершили поддерживаемый API/copy/download / начали share flow | Не фактическое число получателей или визитов |

Стартовые продуктовые ориентиры для проверки, не индустриальная норма:

- First starter win: примерно 75–90% у целевой novice-группы; значение ниже сигнализирует трудность/обучение, выше не автоматически плохо.
- Median first-group time: ориентир 20–45 s; важнее отсутствие долгого непонимания, чем гонка на скорость.
- Основная короткая сессия: ориентир 2–6 min на доску, с отдельными хвостами и доступностью; не лимит времени.
- Voluntary next: первоначальная гипотеза ≥50% после первой победы, но сравнивать с baseline и интервью, не вводить блокирующий релиз процент на маленькой выборке.
- Обоснованная нерешённая неоднозначность starter/calendar board — blocker независимо от среднего win rate.

Для A/B сначала получить baseline и решить минимально значимый эффект, затем рассчитать sample size/срок. Не запускать одновременно новый баланс, новую экономику и новый интерфейс и приписывать весь эффект одному цвету кнопки. Для маленького продукта последовательное наблюдаемое улучшение часто честнее формального A/B с недостаточным N.

### 14.3. Сценарий человеческой проверки

Участнику не показывать решения. Задания:

1. «Откройте игру и начните так, как вам кажется естественным». Наблюдать, найдёт ли старт.
2. После первой группы: «Что произошло и почему?» Не обучать до ответа.
3. Дать следующую starter/первую medium: понимает ли Tabs и бесплатный Wink; проверить добровольный выбор момента.
4. В одной board получить естественную ошибку, затем попросить проверить ту же четвёрку повторно: UI не должен наказать дважды.
5. После результата не говорить «сыграйте ещё»; наблюдать добровольный выбор. Затем отдельно спросить причину.
6. Открыть loss-result на тестовой попытке: участник различает Retry и Another puzzle, понимает раскрытую связь.
7. Вернуться в menu: понимает ли различие daily и practice; узнаёт ли свою коллекцию.
8. На второй день проверить самостоятельное возвращение без обязательной записи на сеанс; исследовательское приглашение учитывать отдельно.

Выход: issue list с цитатами без персональных идентификаторов, board IDs/content versions, severity, frequency/denominator, выбранное изменение и повторная проверка. Одна жалоба не доказывает плохую board, но воспроизводимая валидная альтернативная группировка требует редакторского решения.

### 14.4. Privacy-aware event contract

**OPS-06 / P1.** Расширить существующий `src/analytics/eventLog.ts`, а не подключать второй трекер.

Минимальные события: `onboarding_started`, `onboarding_step_completed`, `onboarding_skipped`, `attempt_started`, `first_group_solved`, `wink_used`, `attempt_completed`, `attempt_abandoned`, `next_puzzle_started`, `reward_presented`, `share_started`, `share_completed`, `share_cancelled`, `board_feedback_recorded`, `return_observed`.

Allowlisted properties: event schema version, app/content/policy version, язык, контекст, tier/band, first/retry, coarse outcome/error/wink facts, duration bucket, acquisition category если реально известна. `zen` должен быть разрешён в schema, если есть в типе.

- Локальные counters возможны без сети. Внешний event отправляется только после explicit consent с описанием измерения; tracking off — default.
- До согласия не создавать сетевые идентификаторы и не накапливать события для последующей скрытой отправки.
- Не передавать полный attemptId, playerSeed, слова задачи, подробный trace ходов, raw профиль или произвольный текст feedback по умолчанию.
- Для board-quality пилота board ID может включаться только в явно согласованный исследовательский экспорт/схему с минимизацией данных.
- D1/D7 требует локального cohort/return state и достаточной схемы измерения. Внешний pseudonymous participant ID — только отдельный явно описанный вариант исследования, не скрытая доработка существующего opt-in.
- Local-only вариант показывает personal return stats и позволяет добровольный export. Без собранной сопоставимой когорты общий D1/D7 остаётся неизвестным.
- Consent revoke немедленно прекращает новые отправки. Offline/denied events не догружаются задним числом. SDK error не влияет на игру.
- Проверить privacy UI, DNT-политику проекта, request log при deny/revoke и содержимое export. Никакой маркетинговой телеметрии по умолчанию.

## 15. Безопасность, монетизация и эксплуатационные ограничения

**OPS-07 / P0–P2.** Сохранить no-backend/no-account: не обещать серверную защиту локальной экономики. Защитить реальные входы: JSON, URL/hash, storage, iframe/host context, optional injected ad SDK.

- External URL проходит разрешённые протоколы/конфигурацию; никакого `javascript:`/произвольного return URL из share payload.
- Monetization config остаётся единым источником; пустой/невалидный handle скрывает CTA. Не заполнять платёжные реквизиты по догадке.
- Supporter cosmetic flag не открывает gameplay; URL success flag честно остаётся trust-based, не доказательством оплаты.
- Rewarded ad, если существующая интеграция активна, только explicit opt-in и периферийная косметика. Не начисляет Wink, lives, retry или улучшение текущего puzzle outcome.
- Rewarded callback должен иметь собственную idempotency и timeout/error flow; в initial public slice допустимо оставить SDK отсутствующим/feature off. Это не blocker бесплатного ядра.
- Нет autoplay, interstitial, banner или FOMO streak saver.
- Review dependency/license/asset notices, действительные privacy descriptions и CSP/host-path effects; не называть такой scoped review полным security audit.
- Не публиковать logs/backup с персональными данными в release evidence. Для fixtures использовать синтетические профили.

### 16.3. Accessibility и реальные устройства

**TEST-A11Y / MUST.** Keyboard-only путь: открыть игру → выбрать/снять четыре → Submit → Wink → result → share → закрыть dialog → продолжить. Focus не теряется. Screen-reader labels и announcements проверяются хотя бы на доступном desktop reader; mobile reader — отдельный gate при наличии устройства.

Автоматический axe scan — дополняющий, не «доказано соответствие всем стандартам». Текстовые alternatives, контраст, meaningful order, error messages, zoom и reduced motion проверить вручную.

Real-device minimum для web public acceptance: один iOS Safari и один Android Chrome с записью моделей/OS/browser, portrait, длинный текст, tap accuracy, safe area, audio unlock, native share, PWA offline/update. Если доступен только один — второй остаётся deferred, а выпуск обозначается с соответствующим ограничением, не «полностью проверен».

## 17. Поэтапная реализация и зависимости

Для новой программы использовать **W0–W8**, чтобы не спутать её с историческими Sprint 0–7, R* и CQ6. Приоритет P0/P1 — не номер волны. Все волны начинаются аудитом своей зоны и заканчиваются evidence/report. Переход по факту проверок, а не по календарной дате.

### 17.1. Размер работ и управление сроками

Это несколько последовательных продуктовых итераций, не один вечер косметических изменений. До W0 нельзя честно назвать точную длительность: она зависит от настоящих migration fixtures, объёма editorial repair, доступности устройств и людей.

Оценивать каждую FW-задачу после аудита как S/M/L и указывать uncertainty. W1 storage/migration и W2 editorial — основные риски; W7 требует реального календарного окна минимум семь дней после старта соответствующей когорты. Это время наблюдения нельзя ускорить дополнительными coding agents.

Минимальный **внутренний проверяемый slice**: W0 + W1 + starters/daily/selection из W2 + W3. Он пригоден для начала организованного UX-пилота, но не объявляется полным публичным выпуском этого ТЗ. Все остальные обязательные пункты остаются в очереди, а Rive и новые экспериментальные поверхности — deferred.

### 17.2. Правила распределения работы

При исполнении использовать bounded native delegation там, где работа действительно независима. Основная задача держит решения, интеграцию и итоговую приёмку.

- Scope review: только продуктовые границы/ADR, без конкурирующего переписывания плана.
- Engine/persistence implementer: owns application, engine, persistence и их tests; screens только по согласованному интерфейсу.
- Frontend implementer: owns tokens/screens/components конкретного slice; не меняет reward semantics.
- Content designer: owns конкретно перечисленные draft boards/metadata; independent validator не тот же автор; promotion только после editor decision.
- QA: read-only проверки и evidence; найденные дефекты возвращаются владельцу, а не исправляются параллельно в чужих файлах.

В каждом brief: точные файлы/ответственность, входной контракт, критерии, команды проверки, известный dirty state; запрет откатывать чужие изменения. Сначала согласовать типы, потом параллелить UI и core. Не запускать отдельного работника ради одной тривиальной правки.

### 19.2. Release evidence record

Путь: `docs/release-evidence/<release-id>/README.md`, связанный с отчётами/артефактами. Содержимое:

- Commit SHA и описание dirty/untracked исключений. Для deployed build — источник фактического артефакта и проверяемый build ID; нельзя назвать один SHA, развернув неподписанный другой worktree.
- Реальный согласованный staging URL и base path; production URL отдельно, если публикация действительно выполнена.
- App/content/calendar/schema/reward/balance policy versions.
- Сценарии happy/error/recovery и test IDs; результаты exact deployed commit.
- Screenshots по трём обязательным размерам и языкам; zoom/device/OS/browser. Короткое замечание по каждому набору, не просто папка PNG.
- Keyboard/focus/labels/errors/contrast; реальные устройства и честно отсутствующие устройства.
- Scripts/build/unit/E2E/audio/validators с результатами.
- Privacy/inputs/monetization/license checks в пределах выполненного review.
- Migration/backup/restore, versioned calendar/content availability, offline/SW update.
- Performance trace/network budget и условия теста.
- Human-balance report и неизвестные retention metrics.
- Rollback target/artifact/schema compatibility; кто принимает Go/No-Go.
- Любой failed/unverified/deferred gate — явно перечислен. Не маркировать «полностью готово» при незакрытых обязательных gates.

### 19.3. Rollback без уничтожения прогресса

**OPS-08 / MUST.** Различать rollback frontend assets и rollback data schema.

1. Перед migration сохранить локальный versioned backup; на staging проверить восстановление на синтетическом старом профиле.
2. Новый frontend должен распознавать supported schema range; несовместимый — открывать безопасный recovery/обновление, не писать defaults.
3. Нельзя публиковать произвольный старый commit, не умеющий новую persistence schema. Готовить совместимый rollback artifact или оставлять migration-aware shell.
4. Старые legacy-клиенты, уже открытые до migration, могут продолжать писать свои старые localStorage keys; эти ключи после успешной migration не являются authoritative и не импортируются автоматически повторно. Перед migration/update предложить закрыть устаревшие вкладки; диагностировать конфликт, не обещать невозможное удалённое управление старым кодом.
5. Content/calendar версии rollback обязаны включать уже опубликованные daily entries и payloads. Не пересобирать календарь «как было раньше» с потерей сегодняшней задачи.
6. На staging выполнить: старый профиль → migration → win → update → compatible rollback → resume/result/collection. Receipt не дублируется, данные не исчезают.
7. Production rollback является отдельным операторским действием в рамках предоставленного разрешения. Этот документ не запускает его.

### 19.4. Severity и стоп-условия

| Класс | Примеры | Решение |
|---|---|---|
| Critical | Потеря сохранения, duplicate rewards штатным путём, неправильная группа, неверный daily, paid gameplay advantage | No-Go до исправления и regression test |
| Major | Нечитаемые слова mobile, недоступный Submit/focus, спорный starter, offline cold boot не работает при обещанной доступности | Блокирует соответствующий public slice |
| Minor | Декоративная неровность, второстепенный asset/legacy-theme polish без влияния на действие | Возможная явная отсрочка с owner; не скрывать |
| Experiment | Motion без доказанной пользы, Rive, дополнительный serif, новые коллекционные иллюстрации сверх необходимого | Не включать в critical path |

## 20. Открытые решения и рекомендуемые defaults

Ниже не вопросы, блокирующие написание ТЗ: для каждого уже выбрано рабочее направление. При реализации существенное отклонение фиксируется до изменения данных/UX.

| Решение | Default | Когда пересмотреть |
|---|---|---|
| Atomic storage | IndexedDB repository, маленький типизированный слой | Только если compatibility spike показывает реальную невозможность на поддерживаемой платформе; не отказываться от атомарности молча |
| XP | 80 за первый eligible unique solve, без Wink penalty | Пилот показывает непонятность; XP остаётся исключительно косметическим |
| Legacy Ink/Wax | Сохранить и показывать в истории, новые grants/spends off | Только отдельное осмысленное продуктовое решение, не магазин ради остатков |
| Mastery | Medium, одна ошибка разрешена, loss на второй, free Wink | Человеческое понимание/интерес; не усиливать через ставки |
| Стартовые доски | 6 на язык, конкретные manifests | После редакторской/человеческой проверки, с версионированием дорожки |
| Daily coverage | 30 дней/язык в опубликованном manifest; 7 дней offline prefetch | По фактическому качеству контента и бюджету кеша |
| Calendar после горизонта | Честная недоступность + практика | Новый заранее опубликованный календарь, не скрытый random fallback |

| Rive | Deferred за пределы обязательного public slice | Основная игра принята, есть конкретная художественная задача и измеренный runtime budget |

| D1/D7 | Неизвестны до достаточной согласованной когорты | Реальные наблюдения, а не forecast или бот |

## 21. Definition of Done для всего ТЗ

Работу можно считать выполненной в заявленном объёме только когда:

1. P0 целостности и сохранений закрыты воспроизводимыми regression tests, migration fixtures и two-tab checks.
2. Daily стабилен; starters и рекомендуемая практика используют принятый редакционный контент; нет известной спорной стартовой/calendar board.
3. Урок, Wink, ошибки, Retry/Another, win/loss и режимы понятны в реальной игре, а не только в документации.
4. Menu → Game → Result действительно перерисован в единую систему и визуально принят на обязательных viewport/языках; доступность не ухудшена.
5. Награды/коллекция/legacy сохранения соответствуют одной policy; ни replay, ни import штатно не дублируют XP.
6. Движение и звук управляемы, отключаемы и не блокируют игру; idle loops отсутствуют.
7. Share/QR/import имеют корректные bounds, preview/error/cancel paths и не выдают локальные данные за проверенную сетевую статистику.
8. Реальные build/perf/offline/update и exact-staging gates имеют evidence; rollback не разрушает новую schema.
9. Privacy и монетизация остаются в установленных границах; внешнее измерение добровольное.
10. Человеческий пилот проведён либо его отсутствие явно ограничивает статус. Нет обещания доказанной «затягивающей игры» без наблюдений. Retention-гипотезы подтверждены, опровергнуты или честно остаются неизвестными.
11. TODO, ADR, schema, limitations, release notes и evidence соответствуют фактическому состоянию; OPTIONAL/P3 не маскируют обязательные незавершённые пункты.

**Первое действие при переходе от плана к исполнению:** FW-001–003, затем FW-004–008. Начинать с анимационной библиотеки, нового магазина или расширения числа режимов до исправления результата/сохранений не следует.
